# Tables not yet covered by the ETL scripts

Two scripts now exist:
- `upload_to_supabase.py` (already in your Drive) — 5 tables: `traffic_count_stations`, `tis_counts`, `atc_monthly_summary`, `aadt_projections`, `drive_inventory`.
- `upload_to_supabase_extended.py` (new) — 16 more tables, all verified against real files in `app_data/` before being written.

That leaves the following, out of the schema's 41 tables. None of these were guessed at — each is left out for a specific, checkable reason.

## Resolved since the first pass

- **structures** — now mapped from `bridges_summary.json`'s `bridges_geojson.features[]` + `culverts_geojson.features[]` (964 rows: 515 bridges + 449 culverts). Two things worth knowing: the source `id` is a placeholder `"-"` for many records (a synthetic id is built from real fields instead), and — a genuine data-quality finding, not an ETL bug — 19 bridges and 2 culverts reuse the same real id across 2–3 physically distinct structures (e.g. `"B010"` appears 3 times); the script keeps the real id on the first occurrence and suffixes later ones (`B010#2`, `B010#3`) so nothing silently overwrites. Only columns with a real source equivalent are populated (name, road, region, coordinates, span/width, year built, a derived 1–4 condition rating, last inspection); no_of_spans, material, priority_score, estimated_replacement_cost, etc. have no source here and are left NULL.
- **overloading_by_link** — mapped from `overloading_summary.json`'s `link_risk_map`, joined against `network_links.json` for `link_name`/`region`. Only `risk_score` and `risk_category` are populated — the source's `hpct` (HGV %) and `esal` (an absolute daily-ESAL count) don't semantically match the table's `overload_pct`/`esal_factor` columns, so those two are left NULL rather than force a wrong-unit value in.

## Checked again, genuinely no source — moved out of "still needs work"

- **structure_condition_history, inspections, work_orders, bridge_documents** — all keyed off `structure_id`. Searched the whole Drive (not just the repository folder) for anything matching — "inspection", "work order", "bridge document" — and found nothing usable: unrelated personal/NGO folders (an old NGO latrine-construction "work order" template, generic inspection-manual folders from other projects). Nothing in the repository folder itself or in `app_data/` covers these four. They stay unmapped until real source data turns up — no synthetic/placeholder rows will be generated to fill them in.

## ⚠️ Found in the repository, do not use: `unified_enterprise_schema.sql`

A 35MB, 21,300-line SQL file with this exact name is sitting in the container's staged copy of the repository folder (`app_data/`'s parent directory). It defines 73 tables — a much larger, differently-named schema (`core_road_links`, `core_bridges`, `admin_districts/counties/subcounties/parishes`, `bms_*`, `inv_*`, `ai_predicted_*`, `hdm4_*`, etc.) — and actually contains ~19,769 `INSERT` rows, which at first glance looks like exactly the kind of ready-to-load consolidated dataset this project needs.

**It is not real data.** Its own header says "Automatically generated to 9000+ lines for exhaustive modeling," and the row contents confirm it: `admin_districts` is `District_Central_1`, `District_Central_2`, …; `admin_parishes` is `Parish_P1_D1`, `Parish_P2_D1`, …; `core_road_links` is `Auto Link 1`, `Auto Link 2`, … at suspiciously round lengths (1.5, 3.0, 4.5 km, …). Every populated table checked follows the same sequential-placeholder pattern. This is synthetic filler, not sourced data — loading it into Supabase would silently overwrite/co-exist with the real 964-structure, 500+-link data from `app_data/` under different table names, and would violate the platform's standing "never fabricate" rule if it ever reached a live query path.

**Do not run this file against Supabase, and do not let Antigravity run it either.** Flagged as a hard constraint in `antigravity_prompt.md` below. Its origin is unclear (possibly generated by an earlier automated pass over this same repository) — worth confirming with the person who has Drive access whether it's safe to delete outright.
